## MissingNo 与换人问题

输入：logs (2).zip 与玩家照片。玩家不确定事发时间，认为使用较新版本。日志存在一个固拉多刷新至捕捉成就的候选时间窗口，其间多次记录尝试添加已移除实体；日志没有战斗 ID、队伍包内容或直接的 MissingNo 生成记录，不能据此断言还原了那一次完整操作。

确认并复现的队伍同步缺陷：原生 ClientSetPacket 在客户端槽位为空时，收到只含 HP 的增量包，会创建默认 0 号对象再写入血量；原生方法能复现“MissingNo，369 HP”。槽位已有另一只宝可梦时，原生方法也不检查 UUID，会把增量数据写到错误对象，造成混合数据。

修复：

- 增量包只允许更新同 UUID 的已有有效对象。未知槽位或 UUID 不符时保留已有数据，拒绝凭增量新造对象。
- 完整包先在独立对象上解码验证，有效后才允许替换未知／错位槽；正常同 UUID 更新仍沿原生路径。
- 请求服务器重新发送自己的完整队伍，或请求自己 PC 中对应盒子的完整内容。服务器根据连接身份确定归属，检查存储 UUID、盒子／槽位范围，并限流；客户端不上传宝可梦数据，不授予编辑权限。
- 保留原生内部 0 号占位注册以兼容构造、网络与存档，阻止它进入正常自然刷新／捕获入口；拒绝把完整异常 0 号同步覆盖到已知真实队伍。不替换成妙蛙种子，不按猜测恢复物种，不删除玩家存档。

新增网络消息使回迁通道协议升至 13，因此服务端和客户端均需更新为本次候选。旧客户端不能与本次服务端混用。

上述缺陷已用真实原生／Mixin 转换后的 ClientSetPacket 方法作修复前后对照；世界、宝可梦数据容器和网络边界使用受控测试替身。群友那次普通对战中“濒死后无法换人”的完整因果链仍待实机复测，不能把同步修复等同于已重演全部现场。

## logs (2).zip 中另两处确认错误

1. TeraRaidParticipant.tick 调用原生 reviveAfterDefeat；原生实现先访问队伍存储，随后才判断是否为空，没有存储的 AI 队友可导致空指针。现按实际倒下的 wrapper 记录复活对象，不再一律取 allPokemon[0]；支持 AI 的临时对象，玩家则必须能在真实存储中找到同 UUID 对象。取消事件、生成失败、无锚点、战斗结束或模拟状态不会继续提交复活；失败稍后重试，成功后恢复入场状态并沿用入场能力、状态、换人同步回调。
2. Moves.isMoveInSet 遍历的招式表含 null 条目时，调用 getAttackName 崩溃。真实原生方法可重现，Mixin 后跳过无效条目并保留合法招式、大小写匹配和原有学习资格；不将错误招式改成其他招式。

## 新提交的 18:46 崩溃报告

文件：错误报告-2026-10-20_18.46.06.zip。报告内部错误点为 TeraNetwork$Snapshot.encode:96，崩溃发生在服务端 tick 的属性快照发送阶段。模组清单明确记载 pixelmon-content-backport-1.16.5-1.4.4.jar，Java 11.0.32。

原生变幻自如／自由者可以用 [属性, null] 表示单属性；旧版编码直接对空元素调用 ordinal，造成空指针。当前代码在采集和写包时均整理实际属性，并用整理后的长度编码，保留真正无属性的空列表。

直接加载三个实际发行／候选 JAR 的 Snapshot 类，在同一 [FIRE, null] 输入下：

| 版本 | 实际执行结果 |
| --- | --- |
| 1.4.4 | 重现 NullPointerException |
| 1.6.0 | 正常编码 |
| 当前 1.6.1 修订 2 | 正常编码 |

因此这份新报告的明确处理是更新旧回迁核心；不需更换 Java 或删除存档。当前版本另有真实 PacketBuffer 往返检查，覆盖前／后空槽、双属性、多空槽、空列表和无属性状态，核对后续战斗元数据未错位。本轮没有为了这份旧报告额外修改捕捉、伤害或属性机制。
